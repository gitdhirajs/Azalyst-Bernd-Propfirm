## 2. What the paper trader now does (`stop_loss.management: scale_out`, the new default)

All levels are in R of the **planned** risk `|entry - stop|`, measured from the **planned** entry.

1. **Before +1R** nothing moves. A stop-out is a full `-1R` (`close_reason = stop`).
2. **At +1R** (`scale_out_at_r`) the bar that reaches `L1 = entry ± 1R` closes 50%
   (`scale_out_fraction`) of the ORIGINAL size at L1 — or at a better gapped open — books it into
   `realized_pnl`, sets `partial_taken / partial_qty / partial_price / partial_time`, halves
   `position_size`, sets `breakeven_triggered` and moves the stop to **breakeven = the fill price**
   from the next bar. L1 is always the PLANNED level (where order A's take-profit rests at the
   broker), also for a stop entry that gapped past the planned entry but not past L1 (review round
   2). A stop entry whose fill is already at/through the planned L1 makes that take-profit
   instantly marketable: the partial is booked AT THE FILL on the fill bar ($0), before the fill
   bar's stop check, and the stop goes to breakeven from the next bar; the FILLED block says so.
2b. **Lot too small to split** (0.01 lots, or `scale_out_fraction >= 1`): run_scanner flags the
   signal `scale_out_unsplittable`, the alert says "PLACE AS 1 ORDER: TP +1R", and the paper trader
   manages that position (`Position.scale_out_single`) as one order: 100% closes at +1R
   (`close_reason = scale_out`), stop never moves.
3. **The runner** (`runner_trail: r_steps`) tracks its peak favourable excursion from bar extremes
   (`Position.runner_peak_r`, persisted). Once the peak reaches +2R the stop locks
   `k = floor(peak_R) − 1` R: +2R → stop +1R, +3R → stop +2R, … from the next bar.
   `runner_trail: none` = the runner rides at breakeven. It has **no take-profit**
   (`runner_target_r: null`, "till possible"); set a number to cap it (`close_reason = runner_target`).
4. **Unchanged conventions:** the stop in force at the bar open is checked first (a gap through
   exits at the open); a bar reaching both the stop and a favourable level counts the stop; the fill
   bar gets no partial or peak credit; a stop move caused on bar k applies from bar k+1; a stop is
   never loosened.
5. **Close reasons:** `stop` (before the partial), `breakeven` (runner stopped at BE),
   `breakeven_gap` (runner's breakeven stop gapped through, exit > 0.05R worse; scale_out only),
   `trail` (runner stopped at a lock), `runner_target`, `scale_out` (single order at +1R). `trade_r_multiple` is the blend over the original
   size: 50% at +1R + runner at breakeven = **+0.50R, counted as a win**; 50% at +1R + runner
   stopped at the +2R lock = +1.50R.
6. **Not in scale_out:** half-T1 breakeven, T1 breakeven, 50% at T2, T3, the `BP_TYPE_LADDERS`
   counter-trend T2 close and `apply_zone_trailing`.
7. **Risk gate:** after the partial `breakeven_triggered` is set, so the runner counts as $0 open
   risk in the daily/total loss budget (unchanged rule, now reached at +1R).

Both pricing paths implement it through the same two methods (`_stop_exit_px`,
`_scale_out_manage`): the 1h bar replay (`BP_BAR_REPLAY`, default) and the legacy single-bar path
(`BP_BAR_REPLAY=0`, `update_positions`); a test checks they agree bar for bar.

`fixed` and `ladder` behave exactly as before when configured. Signal generation is untouched
(the engine still emits 1R/2R/3R targets); no goldtest or engine behaviour changes.
`goldtest/replay_trades.py` reads the live `stop_loss` block, so trade-outcome replays now follow
scale_out too (the Stage-1 goldtest is unaffected).

## 3. Config (`Propfirm Trading Dashboard/BP_config.yaml`)

```yaml
stop_loss:
  management: scale_out        # scale_out | fixed | ladder
  scale_out_at_r: 1.0          # partial trigger, R of planned risk from the planned entry
  scale_out_fraction: 0.5      # fraction of the ORIGINAL size closed at the trigger
  runner_trail: r_steps        # r_steps | none
  runner_target_r: null        # optional runner take-profit in R; null = no cap
  take_profit_target: 2        # fixed only
```

One reader, `BP_management.management_settings()`, is used by the paper trader, `send_discord.py`
and `draw_chart.py`. A MISSING `management` key means `scale_out` (a change from the pre-2026-09-28
code default `ladder`; the live yaml sets the key, so the live bot is not affected). An UNKNOWN value
(e.g. `fixd`) and nonsense scale_out numbers (`scale_out_at_r` / `scale_out_fraction` <= 0 or
unparseable, fraction > 1, `runner_target_r <= scale_out_at_r`) fall back to **`fixed`**, the
conservative set-and-forget bracket, with an ERROR in the log and a `[!] CONFIG:` line in the Discord
footer (review round 2; before, an unknown value silently meant scale_out). `run_scanner` publishes the settings as `results["management"]`, and Discord/charts
use that (falling back to `BP_config.yaml`), so a post always describes the mode the paper trader ran.

**Revert:** set `stop_loss.management: fixed` (the 2026-09-27 behaviour) — no code change needed.
The revert is **config-only while any open position has a booked partial** (`booked_pnl > 0`): the
config revert keeps honouring `booked_pnl`, so nothing is double-counted. A **code** revert (git
revert / older engine) drops `booked_pnl` on load and books the whole `realized_pnl` again at the
runner's close — the partial would be in the balance twice (reproduced: 5046.94 instead of 5035.20
on the live NZDCHF order). Before any code revert run the migration:

```
python research/unbook_partials.py                 # dry run on the live state
python research/unbook_partials.py --apply         # writes, keeps a .bak
```

It takes each open position's booked partial back out of `closed_pnl_total` / `balance` (and
`daily_pnl` when the partial was in the current trading day) and sets `booked_pnl = 0`, so the old
code books it exactly once. Demo on the reviewer's rollback state: 5011.73 -> 5000.00 after the
migration, then old code closes the runner at T2 -> **5035.20** (correct). Test:
`test_unbook_partials_lets_old_code_book_the_partial_once`.

The all-coins tracker (`BP_config_allcoins.yaml`, `_gen_allcoins_config.py`) is pinned to
`management: fixed`, the mode its series ran under, so its win definition does not change mid-series.
